# ROUTE_B_SDK — JSON Output Contracts

**Post-Milestone-1 evidence reconciliation:** fields backed by
`docs/sdk_javap_evidence_register.md` are `CONFIRMED_BY_JAVAP`; earlier `REQUIRED_INPUT`
comments in this historical design are superseded. The only remaining inputs before Milestone 2
are: complete transitive SDK classpath, confirmed read-only BLX/DFX or CMS loading path,
confirmed `DataSource` provider, confirmed `DataFoundation` provider, CMS details only if CMS
retrieval is selected, and remote working/export directories.

**Status:** Design package only. **No Java code is implemented; no JSON has been generated by
this document.** Defines the deterministic JSON contracts the future SDK extractor
(`docs/sdk_component_design.md`) will emit, how they map onto the existing Route A CSV catalogs,
and a gap analysis of which PDF-derived fields Route B can authoritatively replace.

## 0. Common Envelope

Every one of the six JSON files shares this envelope (top-level object), consistent with the
project's existing `RawArtifact` model (`src/bo_semantic_extractor/models/common.py`) and the
`EvidenceVerificationStatus` enum (`src/bo_semantic_extractor/models/common.py`):

```jsonc
{
  "source_system": "string",       // e.g. "BO_SEMANTIC_LAYER_JAVA_SDK"
  "extraction_method": "string",   // e.g. "CmsResourceService.retrieveUniverse+DataFoundation.getJoins"
  "evidence_level": "string",      // "AUTHORITATIVE_SDK" | "DERIVED_PDF" | "UNVERIFIED_CANDIDATE"
  "verification_status": "string",// "CONFIRMED" | "PARSED_UNVERIFIED" | "UNKNOWN"
  "universe_cuid": "string | null",
  "universe_name": "string",
  "extracted_at_utc": "ISO-8601 timestamp",
  "run_id": "string",
  "items": []                       // contract-specific array, see below
}
```

`evidence_level` is new relative to existing project enums and specific to this track: it
distinguishes an SDK-read fact (`AUTHORITATIVE_SDK`) from a PDF-report-derived fact
(`DERIVED_PDF`, for any interim dual-running period) from a pattern-detected, unverified
candidate (`UNVERIFIED_CANDIDATE`, e.g. lineage edges before HANA cross-reference).

**Never included, by design:** any field derived from `DatabaseConnection.PASSWORD` or full,
unfiltered `getParameters()` dumps. See `docs/sdk_component_design.md` §6.

  "...envelope...": "...",

    {
      "context_name": "string",
      "associated_join_ids": ["string"],   // REQUIRED_INPUT: exact Context accessor for member joins

## 6. `lineage_edges.json`

```jsonc
{
  "...envelope...": "...",
  "items": [
    {
      "object_id": "string",
      "object_name": "string",
      "select_expression": "string | null",
      "referenced_table": "string | null",
      "referenced_column": "string | null",
      "physical_hana_object": "UNKNOWN",     // never fabricated; only HANA cross-reference (out of scope) can populate this
      "physical_hana_column": "UNKNOWN",
      "evidence_level": "AUTHORITATIVE_SDK | UNVERIFIED_CANDIDATE",
      "verification_status": "CONFIRMED | PARSED_UNVERIFIED | UNKNOWN"
    }
  ]
}
```

Even with a confirmed, structured `select_expression` from the SDK (vs. Route A's PDF text),
`referenced_table`/`referenced_column` remain `PARSED_UNVERIFIED` at best until HANA catalog
cross-reference occurs — Route B improves *evidence quality* of the expression itself, not the
lineage verification status, which is unaffected by this design (per
`docs/universe_lineage_acquisition_strategy.md` §5).

## 7. Mapping Existing CSV Catalogs to Future SDK Contracts

| Existing Route A file | Future Route B contract | Row-level mapping |
|---|---|---|
| `object_catalog.csv` | `business_layer.json` | `object_id`→`object_id`, `object_name`→`object_name`, `object_type`→`object_type`, `folder_path`→`folder_path`, `description`→`description`, `source_system`→replaced by `source_system`+`evidence_level` |
| `expression_catalog.csv` | `business_layer.json` (merged) | `select_expression`→`select_expression`, `where_expression`→`where_expression`, `projection_function`→`projection_function` |
| `table_catalog.csv` | `data_foundation.json` | `table_name`→`table_name`, `table_type` (`UNKNOWN`/`derived`/`view` under Route A) → `table_type` (`standard`/`alias`/`derived`, fully resolved under Route B) |
| `join_catalog.csv` | `join_metadata.json` | `join_id`→`join_id`, `left_object`/`right_object`→`left_table`/`right_table`, `join_expression`→`join_expression`, `join_type`/`cardinality` (`UNKNOWN`/`UNKNOWN` under Route A) → `outer_type`/`cardinality` (resolved under Route B, pending the two `REQUIRED_INPUT` accessors) |
| `lineage_catalog.csv` | `lineage_edges.json` | Same shape; `select_expression` source improves from PDF text to SDK-structured text, `verification_status` semantics unchanged |
| *(none — new in Route B)* | `connection_metadata.json` | Not produced by Route A at all; Route A's design inventory only found connection name/path/server as PDF text (`docs/dm_invoice_data_mart_design_inventory.md` §6), with `driver_type`/`database_type` `UNKNOWN`/`PARSED_UNVERIFIED` |
| *(none — new in Route B)* | `context_metadata.json` | Route A confirmed `Contexts (0)` from PDF text alone; Route B would confirm the same fact structurally via `getContexts()` |

## 8. Gap Analysis — Which PDF-Derived Fields Route B Authoritatively Replaces

| Field (Route A status today) | Route B status (once `REQUIRED_INPUT` accessors are confirmed) | Closes a real gap? |
|---|---|---|
| `join_catalog.csv.join_type` — `UNKNOWN` for 34/34 joins | Resolved via `OuterType` (accessor `REQUIRED_INPUT`, but the type is confirmed to exist) | **Yes — highest-value gap.** Route A can never resolve this (rendered as an icon in the PDF). |
| `join_catalog.csv.cardinality` — `UNKNOWN` for 34/34 joins | Resolved via confirmed `Cardinality` enum (`CUNKNOWN`/`C1_1`/`C1_N`/`CN_1`/`CN_N`) | **Yes — highest-value gap.** |
| `table_catalog.csv.table_type` — `UNKNOWN` for 35/39 rows (alias-vs-standard undetermined) | Resolved via `instanceof` check against `DatabaseTable`/`AliasTable`/`DerivedTable` | **Yes.** |
| Derived table SQL (`REQUIRED_INPUT`/not present at all in Route A) | Available via `DerivedTable`'s SQL accessor (`REQUIRED_INPUT` exact name, but the value itself is stored on the object per `createDerivedTable(name, sql, dataFoundation)`) | **Yes**, once the accessor is confirmed. |
| Alias table's aliased-table name (Route A: hypothesis only, e.g. the customer-table family in the design inventory) | Available via `AliasTable`'s accessor (`REQUIRED_INPUT` exact name, but the relationship is confirmed to exist: `createAliasTable(name, aliasedTable, dataFoundation)`) | **Yes**, once the accessor is confirmed — this directly resolves the `PARSED_UNVERIFIED` hypothesis in `docs/dm_invoice_data_mart_design_inventory.md` §3.1. |
| The 22 undetailed filters (83 declared, 61 printed in the PDF) | Route B reads every filter object directly from the Business Layer — no PDF report page-limit applies | **Yes**, assuming these 22 filters exist in the live `.unx` and were simply omitted from the PDF export (an assumption to verify, not a certainty). |
| 13 declared Parameters (0 detailed in the PDF) | Route B reads every `Parameter` object directly (`isUserPrompted`, `getPromptText`, `getDataType`, `getAssociatedLov` — setters confirmed, getters inferred) | **Yes**, same caveat as above. |
| 21 declared Lists of Values (0 detailed in the PDF) | Route B reads every `Lov` subtype directly (`StaticLov`/`SQLQueryLov`/`BusinessQueryLov`/`BusinessHierarchicalLov`, all confirmed classes) | **Yes**, same caveat. |
| Database type / middleware (Route A: `PARSED_UNVERIFIED`/`UNKNOWN`, only a change-log comment mentions "Hana") | Resolved via `DatabaseConnection.getParameter(DBMS)` / `getParameter(NETWORK_LAYER)` | **Yes — fully confirmed accessors, no `REQUIRED_INPUT` remaining for this field.** |
| The `View 0` vs. `Views (1)` discrepancy (design inventory §3.2) | Resolved via `DataFoundation.getMasterView()` (always present) + `getDataFoundationViews()` (additional custom views) — the discrepancy likely reflects the PDF conflating "custom views" (0) with "master view" (always 1, uncounted in that statistic) | **Likely resolves the discrepancy**, pending confirmation once Route B is implemented. |
| Physical HANA column verification | **Not** closed by Route B | **No.** Route B still stops at the Data Foundation table/column level; HANA catalog cross-reference remains a separate, later stage per `docs/universe_lineage_acquisition_strategy.md`. |

## 9. Non-Goals of This Document

No JSON has been generated; no Java code implements these contracts yet. Every `REQUIRED_INPUT`
marker above names the exact class whose Javadoc page must be fetched and confirmed before that
field can be implemented — none of those accessor names are asserted as fact.
